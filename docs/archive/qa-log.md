# 第一部分 · 前置对话（问题诊断）

## Q-A1 为什么大家都用 agent 辅助编程，同一个赛题的实际效果差别却这么大？

**结论**：「说得细不细」不是决定因素，真正决定的是**你在约束目的，还是在约束手段**。

你观察到的两种失败，成因不同：

| 现象 | 真正成因 |
|---|---|
| 说得太细，它顺着固化思路走、越走越偏 | 你提前写死了**实现路径**。它不是固执，是你在许可它做**局部优化** |
| 说不细，出现幻觉/过度扩散/偏离目标 | 你没写清**验收标准**。它既不知道什么算成功，也不知道边界在哪 |

**关键拆解**：细节有两个维度，作用方向相反。

- **对目的的约束**（要达成什么、什么算成功、硬性限制、不能碰什么、已知的坑）→ **越细越好，几乎没有上限**
- **对手段的约束**（用什么算法、什么结构、分几步、代码长什么样）→ **默认留空**

所以不存在「细和粗之间找一个平衡点」这回事。

## Q-A2 第一个原因（调参经验）站不站得住？

**结论**：这个判断大概率被**低估**了，不是高估。

调参的本质是**把「手感」变成「可测目标函数 + 可复现实验」**。很多人练了很多次，但一直是盲调（改一个参数、跑一次、凭感觉判断）。这种练习**不产生收敛性提升**，练十次和练一次差不多。

真正的差距在四件事：

1. 固定起点、固定场景的测试流程
2. 日志与曲线，能把「顺了一点」变成数字
3. 一次只改一个变量
4. 能区分「硬件个体差异造成的现象」与「代码问题」

**放大器**：校赛层级中，硬件一致性、机械装配、场地差异带来的方差可能**大于代码方差**。很多「别人做得就是好」的印象，来源是测量和实验设计的投入，不是代码复杂。

---

## Q-A3 第二个原因（表达习惯）是不是主因？

**结论**：有影响，但大概率**不是主因**，而且在长期**贬值**。

理由：模型在变强，对措辞的鲁棒性在提高。所以「边界怎么明确」这个问题只落在整条链的**最后一环**。把它当成核心问题 = 优化错地方。

---

## Q-A4 边界能不能消除？

**结论**：**不能消除**（沟通必然有损耗），但可以**变便宜**——把它变成可检测、可回退的错误，而不是要竭力避免的错误。这就是工程和赌博的区别。

判断该收该放的三个量：

| 变量 | 含义 | 用法 |
|---|---|---|
| **可验证性** | agent 能不能自己跑出对错 | 能 → 手段大胆放开；不能 → **先去补验证手段** |
| **可逆性** | 改错了回退多贵 | 低 → 放手探索；高 → 先对齐再动手 |
| **你已有答案的程度** | 你确不确定怎么做 | 确定 → 直接下指令；不确定 → **显式切到探索模式** |

> 「利用它的知识库帮我找新思路」这件事应该做成**显式的模式切换**，而不是用模糊表达去碰运气：模糊是概率，模式切换是可控。

## Q-A6 高性价比的七条操作（按性价比排序）

1. **动手前先让它复述**：「用你自己的话复述我的目标，列出你不确定的 3 个点，说明你打算怎么验证成功。先不要写代码。」——误解题意几乎总发生在前两句，越晚发现越贵。
2. **写死验收标准，放开实现**。
3. **发散/收敛分成两个显式阶段**：「现在是发散阶段，不要写代码」／「现在是收敛阶段，按方案 B 实现，不要改架构」。
4. **目标放进文件，不要只放对话里**（对话会被上下文压缩）。
5. **投入反馈带宽**：让它能编译、能跑、能拿日志/曲线。**agent 的上限由它看到的信号决定，不由你的措辞决定。**
6. **方向错了就回退重开**，不在错误方向上叠补丁（感到「越走越难」时八成已该回退）。
7. **自己保留心智模型**：读 diff，不要只看「跑通了」。

## Q-A7 对「我总结的第 1 点」的修正

**你的原话**：细的是验证方案、硬件配置、串口；粗的是算法、结构、组织。

**修正**：**结构恰恰是你唯一能自己验证的东西，不能放开。**

| 层 | 内容 | 松紧 |
|---|---|---|
| 层 1 接口层 | 契约、单位、坐标系、频率、异常语义、串口协议 | **钉死** |
| 层 2 编排层 | 数据流向、模块切分、配置外置、日志与记录 | **半固定** |
| 层 3 算法层 | 用什么方法、什么参数 | **完全放开** |

> 口诀：**层 1 写到能写测试，层 2 只定步骤不定实现，层 3 一句话不提。**

## Q-A8 你说「小白不知道什么验证方案合理」→ 用验证阶梯

任何需求必须能落到某一级，**落不到任何一级的需求 = 没想清楚的需求**。

| 级 | 做法 | 需实地？ | 成本 |
|---|---|---|---|
| L0 | 能导入、能启动、跑通全链路 | 否 | 分钟 |
| L1 | 单元测试（固定输入 → 固定输出） | 否 | 十分钟 |
| L2 | 离线回放（golden 集跑完整 pipeline） | **否** | 小时 |
| L3 | 台架（相机对已知尺寸靶标） | **否**（书桌即可） | 半天 |
| L4 | 装车不动（只测通信与延迟） | 是 | 半天 |
| L5 | 装车跑动（重复 N 次统计） | 是 | 若干小时 |

验收标准写三要素：**现象 + 数值 + 条件**。

- ❌「能准确识别货物」
- ✅「在 ⟨光照⟩ 下、距离 ⟨0.3–1.2m⟩、目标静止，连续 100 帧中位置误差 ≤ ⟨1cm⟩ 的帧占比 ≥ 90%」

## Q1 离线回放和黄金数据的判断标准是什么？条件所限无法模拟真实比赛情景怎么办？

### 1.1 判断标准不是「复现」，是「覆盖」

离线回放验证的是**算法对输入的不变性**，不是「比赛表现」。所以不需要还原现场全部细节，只需要覆盖你认为**会变化的维度**。

**做法：把场景拆成正交维度，不做全组合。**

| 维度 | 取值举例 |
|---|---|
| 距离 | ⟨0.3 / 0.6 / 1.0⟩ m |
| 方位 | 左 / 中 / 右 |
| 光照 | 正常 / 偏暗 / 逆光 |
| 背景 | 干净 / 杂乱 / 同色干扰 |
| 遮挡 | 无 / 露一半 |

组合出 12~20 个样本就够。

### 1.2 真正不能妥协的是「几何不变量」

**同相机、同镜头、同安装高度、同俯角。** 场景可以变，几何关系不能变。

理由：离线回放的坐标变换依赖内外参，一旦镜头或安装位姿不同，米制误差就失去意义。**这条不满足，L2 的指标全部不可信。**

### 1.3 「做不到」怎么处理

写进 `docs/gaps.md`，三栏：缺哪个维度 / 风险等级 / 用什么补（L4 或 L5）。并明确「哪些指标现在不能信」。

**这是正确做法，不是妥协**：把未知显式化，比假装覆盖到了安全得多。

### 1.4 两级阈值

- **gate（通过/不通过）**：硬阈值，不达标不许合入。例：`pos_err ≤ 1cm 的帧 ≥ 90%`
- **eval（趋势）**：看指标是否退化（回归），绝对目标以 L5 实测为准

## Q2 假数据源是一套完全虚拟的脚本？不上实物测有什么意义？

### 2.1 你的理解正确

它就是一个**和真相机接口完全相同、但不接硬件的实现**：返回生成图（全黑 / 画方块 / 静态图）+ 递增的假时间戳。

### 2.2 它测什么、不测什么

| 它能测 | 它不能测 |
|---|---|
| 接口接线是否正确（字段齐不齐、类型对不对、契约符合否） | 识别准确率 |
| 下游能否正常消费（状态机、序列化、串口打包） | 坐标精度 |
| 边界与崩溃（`None`、空列表、`LOST`、超长消息） | FPS / 延迟 |
| 队友在没有你的算法时能否开工 | 任何真实场景表现 |

**一句话：它是「接线测试」，不是「效果测试」。**

### 2.3 为什么必要

1. **让错误可归因**。第一行算法和第一次接线的错误混在一起时，你分不清是谁的错。有假源，就能先把下游全部验证干净，之后出问题必然在算法里。
2. **让 L0 第 1 天就能完成**。没有相机、没有场地、队友还没到位时也能推进。
3. **类比**：电路里的信号发生器。没有它也能调试，但每次都要真实信号源，成本高且不可控。

### 2.4 边界

假源不能替代 L2。**它证明「管道通」，不证明「算法对」。** 两者都要。

## Q3 三个检查点的思路是什么？代码里的数字指什么？怎么让表达准确？怎么知道问题解决？怎么防连锁破坏？

### 3.1 检查点的思路：越权检测，不是质量检测

这是关键区分：

| 类型 | 靠什么 | 能否自动化 |
|---|---|---|
| **质量检测**（它对不对） | L1/L2 验证 | 能（`eval.py`） |
| **越权检测**（它有没有绕过你的约束） | 结构巡检 | 不能，靠人扫一眼 |

我给的三个点是**越权检测**。质量问题交给验证方案，不要浪费注意力。

### 3.2 「代码里的数字」是什么——魔数（magic number）

指：**本该从 `configs/*.yaml` 读的参数，被直接写死在代码里。**

```python
# 错误：conf_thr 从哪来的？没人知道
if conf > 0.5: ...

# 正确
if conf > self.cfg.thresholds.conf_min: ...
```

**这个数字是怎么出现的**：agent 为了让代码「先跑起来」，会硬编码一个看起来合理的值。它不是恶意，是**效率优先的默认行为**。

**为什么危险**：

1. 你改 yaml 无效（被代码覆盖），且没有任何提示
2. 参数扫描失效（`sweep.py` 扫的是 yaml，代码里的值不动）
3. 你不知道它引入了什么假设——`0.5` 隐含「目标清晰可辨」，一旦场景变差，这个假设失效却无人知晓

**检测方式的可靠性说明**：`grep -n "[0-9]\{2,\}"` 只是**启发式，会大量误报**（`255` 颜色上限、`1000` 毫米换算、`3` 通道数都是合法的）。所以用法是「扫一眼确认」，不是「要求清零」。

**更可靠的手段**：`core/config.py` 启动时**打印全部生效参数及其来源**，看有没有代码默认值覆盖了配置。这个比 grep 准。

### 3.3 怎么让表达准确 → 不追求准确，追求「错误可发现」

这是核心转变。三个位置各设一道网：

| 时点 | 手段 | 作用 |
|---|---|---|
| 前置 | 让它复述目标 + 列不确定点 + 说验证方式 | 抓「理解偏差」 |
| 中置 | 一次只做最小一步 | 抓「扩散」 |
| 后置 | 跑 `eval.py` + 写「假设/限制」三行 | 抓「隐含约束」 |

**「让它写三行」是最被低估的一条**：`改了什么 / 我假设了什么 / 我给什么加了限制`。第三行「限制」它几乎从不主动写——你不要求它写，它就不暴露。

### 3.4 怎么知道问题「有没有解决」→ 让程序回答

**这是你目前最关键的缺口。** 正确流程（固定，不许跳步）：

```
1. 先做出一份能复现失败的样本 → 放进 data/golden/gate/
2. 跑 tools/eval.py → 必须是 FAIL（证明样本有效）
3. 让 agent 改
4. 跑 tools/eval.py → PASS 才算解决
5. 跑全量 tests/ → 防连锁破坏
```

**第 2 步最容易被跳过**，但它决定了后面所有判断是否可信：如果样本本来就 PASS，那 PASS 什么也没证明。

> 原则：**「有没有解决」必须由程序回答，不能由 agent 口头回答。** 它说「应该修好了」不构成任何证据。

### 3.5 怎么防「改一处另一处没改」

三层防线，按可靠性排序：

1. **L1 单元测试**（最可靠）：`test_protocol.py` / `test_geometry.py` 覆盖契约与数学，改错立刻红。
2. **L2 全量回归**：每次改完跑完整 golden，指标不许退化。
3. **引用检查**：要求它改完 `grep` 该符号的所有引用位置并列出。

配套纪律：**每次只允许改一个模块；改完必须全量跑，不许只跑它自己写的那个测试。**

## Q4 我每次改的是硬件配置、串口、参数、车体形态——这些就是契约内容吗？

### 4.1 结论：只有一部分是，必须拆开

| 你改的东西 | 是否契约 | 归属 | 理由 |
|---|---|---|---|
| 串口参数（波特率、分帧、校验） | **是** | 契约 §传输层 | 对方必须知道，否则解不出帧 |
| 相机型号 / 分辨率 / 帧率承诺 | **部分是** | 契约 §时序（频率承诺）+ `camera.yaml`（具体参数） | 对方只关心「能不能按时给数据」 |
| 相机安装位姿（高度、俯角） | **是** | 契约 §坐标约定 | 决定米制坐标含义，对方按它做控制 |
| 阈值、ROI、滤波参数 | **否** | `configs/task.yaml` | 纯内部，对方不需要知道 |
| 车体形态（尺寸、轮距） | **一般否** | 你的 `spec.md` | 除非它改变了相机安装位姿 |
| 平台型号（树莓派/Jetson） | **否** | `spec.md` | 只影响 FPS，而 FPS 本身已在契约里承诺 |

### 4.2 两个判据（比背表更实用）

1. **对方需不需要知道？** 需要 → 契约；只有你算法需要 → 配置
2. **改它之后，对方代码要不要改？** 要 → 契约

### 4.3 一句话记法

> **契约 = 你和对方的边界上流动的东西的形状与含义。**
> 边界内部的东西（阈值、模型、滤波器）再重要也不是契约。

## Q5 「同一个接口的两种实现」我理解对不对？每个文件到底干什么？

### 5.1 你的理解：方向对，有一处关键偏差

**✅ 对的部分**：交付 jsonl 给队友 → 队友写「读 jsonl 当串口输入」的假源 → 在电脑上验证主板逻辑 → 上车换成真相机。

**❌ 偏差**：不是「把 `sink/serial.py` 模拟到 `sink/jsonl.py`」（那会变成一份实现去模仿另一份，格式必然漂移）。

**正确关系**：两者是**并列的兄弟**，共同调用同一个 `core/protocol.py::encode()`：

```python
# core/protocol.py 【层1】唯一编码入口
def encode(msg: VisionMsg) -> bytes: ...

# sink/serial.py
def write(self, msg): self.port.write(protocol.encode(msg))

# sink/jsonl.py
def write(self, msg): self.f.write(protocol.encode(msg).hex() + "\n")   # 或同结构的 json
```

**关键纪律**：**不许任何一份实现自己拼字符串/自己拼字节。** 只要编码只有一个入口，两边内容天然一致。

### 5.2 各文件职责（按你的困惑顺序）

**`core/`（层 1，钉死区，谁都不许改）**

| 文件 | 职责 | 为什么不能改 |
|---|---|---|
| `types.py` | 定义 `VisionMsg`、`Object`、`Status` + `CONTRACT_VERSION` | 这是双方共同的「数据类型」 |
| `protocol.py` | **唯一的**序列化入口 | 多一个入口 = 格式必然漂移 |
| `interfaces.py` | `FrameSource` / `Sink` 两个 Protocol | 这是「可替换」得以成立的前提 |
| `clock.py` | 统一时间源，只认帧时间戳 | 时间戳混乱会让延迟不可测 |
| `config.py` | 加载 yaml + 校验 + **打印全部生效参数** | 这是防魔数的真正手段 |

**`source/`（层 2，帧的来处）**

| 文件 | 职责 | 何时用 |
|---|---|---|
| `camera.py` | 真相机，含缓冲策略（只留最新帧） | 上车 |
| `video.py` | 读 mp4 / 帧序列，附带录像里的时间戳 | L2 离线回放 |
| `fake.py` | 生成假帧 + 假时间戳 | L0、没硬件时开发、队友未到位时 |

**`sink/`（层 2，结果的去处）**

| 文件 | 职责 | 何时用 |
|---|---|---|
| `serial.py` | 发串口 | 上车 |
| `jsonl.py` | 写文件，供回放/交付队友 | L2、联调 |
| `stdout.py` | 打屏幕，最快看效果 | 调试 |

**`perceive/`（层 3，自由区）**

| 文件 | 职责 |
|---|---|
| `base.py` | 插件基类：`detect(frame) -> list[Detection]` |
| `⟨插件⟩.py` | 具体算法，可多个并存，配置切换；**新想法永远新建文件，不改原文件** |

**`geometry/` `decide/`（层 2/3 之间）**

| 文件 | 职责 | 松紧 |
|---|---|---|
| `transform.py` | 像素 → 米、外参变换 | 半固定（数学必须有单测） |
| `filter.py` | 滤波策略 | 放开（可换插件） |
| `state_machine.py` | 比赛任务流程（搜索→接近→对准→完成） | **大幅放手**，改错不污染接口 |

**`app/`**

| 文件 | 职责 |
|---|---|
| `pipeline.py` | 接线：`source → perceive → geometry → decide → sink`。**只认接口，不认识实现** |
| `main.py` | 入口，读 `runtime.yaml` 决定用哪套 |

**`tools/`（全部是 agent 可直接执行的命令）**

| 文件 | 职责 | 谁跑 |
|---|---|---|
| `record.py` | 录原始帧 + 时间戳 | 你 |
| `replay.py` | 离线重放，逐帧跑完整 pipeline | agent |
| **`eval.py`** | **喂 golden → 输出 PASS/FAIL + 指标** | **agent（最关键）** |
| `sweep.py` | 参数扫描出表 | agent |
| `calibrate.py` | 内参/畸变标定 | 你（要摆靶标） |

### 5.3 `pipeline.py` 到底指什么（避免和第 2 问的混淆）

`pipeline.py` = **接线**（取图 → 感知 → 几何 → 决策 → 输出这条**数据通路**），
**不是**比赛任务流程（搜索 → 接近 → 对准）。后者在 `decide/state_machine.py`。

这个区分直接决定松紧：

| | 属于 | 能否放手 |
|---|---|---|
| `pipeline.py` 接线 | 基础设施 → 层 2 | 不能全放（它决定能否回放、能否换算法） |
| `state_machine.py` 业务流程 | 业务逻辑 → 层 2/3 之间 | **可以大幅放手** |

## Q6 黄金数据到底是什么？gate 是失败图片吗？eval 怎么拍？怎么标注？

### 6.1 gate 集 ≠「失败图片集合」

准确说法：**「必须成功的场景」+「已知容易失败/已踩过的坑」**，两类混在一起。

| 类型 | 例子 | 期望 |
|---|---|---|
| 基准帧 | 最正常的那一帧 | 必须 PASS |
| 已知失败模式 | 逆光、露一半、反光、极小目标、同色干扰 | 修前 FAIL，修后 PASS |

**两条收录判据（必须同时满足）**：

1. **你知道正确答案**（人工核实过，不是模型跑出来的）
2. **它对应一个具体失败模式或一条关键路径**

### 6.2 最重要的机制：生长

> **每修好一个 bug，就往 gate 集加一帧。**

这样覆盖度随项目自然增长，你不需要一开始就预见所有情况。**这才是「怎么挑最有代表性」的真正答案**——你一开始确实答不出来，但每次踩坑都答得出来。

### 6.3 eval 集：手持模拟可以，但有三个约束

| 约束 | 说明 |
|---|---|
| **同几何** | 同相机、同镜头、同安装高度、同俯角（这条不可妥协） |
| **只拍任务阶段** | 开机、自检、纯行驶画面没有视觉信息量，只会稀释指标 |
| **必须含「接近阶段」** | 目标由远到近、逐渐进入视野的过程——它决定「第一次检出」的时刻 |

所以正确做法：**分段拍摄**，每段标注阶段名，例如 `20261028_desk_approach_01.mp4`。
不要「从开机开始一路录」。理由：混入无效帧会让「检测率」这类指标失去意义（分母被稀释）。

### 6.4 无法完全复刻现场怎么办

记入 `docs/gaps.md`：缺哪个维度 / 风险等级 / 用什么补。然后：

- 缺光照维度 → 用台灯 + 遮光布近似，或标为风险，用 L4 补
- 缺真实背景 → 用相近颜色的布料/纸板近似，或标为风险
- 缺动态模糊 → 手持快速移动可部分模拟，或标为风险

**底线**：几何不变量（相机/镜头/安装位姿）不能妥协，其余都能近似 + 记账。

### 6.5 标注：按任务类型分三档，成本差别巨大

| 任务类型 | 要标什么 | 成本 | 说明 |
|---|---|---|---|
| 只要「识别对不对」 | **文件名编码期望值**，脚本比 `cls` | ≈0 | 例 `red_01.png` 期望 `cls=red` |
| 要像素定位（圆环中心、物料框） | 中心像素 + **容差**（例 ±15px） | 几分钟/张 | 手工点两下 |
| 要米制精度 | 卷尺量真值距离，写 `labels.yaml` | 每样本实测 | 只有需要 cm 级时才做 |

**你的两个具体场景：**

**① 不同颜色物料**
- 若任务只是「分拣到对应颜色区域」→ 只需**分类正确性** → 用文件名编码，零标注成本
- 若需要「对准抓取」→ 加中心像素容差
- 关键：`red` 的定义要写死在 `labels.yaml`，不要让 agent 自己决定「什么算红」

**② 找指定圆环**
- 标**中心像素 + 半径**（或 bbox），容差按任务定
- 若只需要「有没有找到」，那 golden 就退化成布尔判定：`found: true/false` + 一个可接受的中心容差
- 注意：如果有多个圆环，必须标「哪一个是对的」——**目标选择本身就是算法的一部分**，不标清楚你永远不知道它是在测「检测」还是「选择」

**绝对禁止**：用模型自己跑出来的结果当标签（循环论证，永远 PASS，什么也没测到）。

### 6.6 gate 与 eval 的分工表

| | gate | eval |
|---|---|---|
| 数量 | 5~10 | 100+ 帧 / 3~5 段 |
| 用途 | **PASS/FAIL 闸门** | 指标趋势（检测率、误差分布、FPS） |
| 变动 | 只增不减 | 可替换，但换了失去可比性 |
| 通过条件 | 全部必须过 | 不低于上次 |

## Q7 元信息里的 `status` 起什么作用？会不会让流程太繁杂？

### 7.1 作用：把「数据有效性」的判断从接收方转移到发送方

没有 `status` 时，接收方只有两种选择：要么只看 `conf` 猜，要么什么都不判断（危险）。有了它，**「这帧能不能用」变成一条显式信息**。

**它防的是最危险的一类事故**：接收方拿着过期/无效数据继续做动作（车冲出去）。这比字段精确度重要得多。

### 7.2 三个就够，不要更多

| 状态 | 含义 | 接收方必须做什么 |
|---|---|---|
| `OK` | 数据可信 | 可全速动作 |
| `DEGRADED` | 有数据但质量低（部分遮挡 / 低置信度） | 降速、保守动作 |
| `LOST` | 无可信目标 | 停止或进入搜索，**禁止沿用上一帧** |

### 7.3 会不会繁杂？——繁杂的来源不是数量

```
繁杂 = 状态数量 × 每个状态需要定义的行为
```

真正的工作量在第二项。**只要不超过 3 个，且每个状态的行为一句话能说清，就不繁杂。**
若队友主板逻辑很简单，可退化成 `OK / LOST` 两态（甚至一个布尔 `valid`），保留「禁止沿用上一帧」这条语义即可。

### 7.4 必须配套的一条

契约里**每个状态都要写「接收方必须怎么处理」**。只定义枚举不定义行为 = 白定义，两边各按自己理解实现，联调时必吵。

## Q8 字段清单只是清单，还是也控制参数？

### 8.1 结论：只是结构清单，不控制参数。但它**间接约束**参数语义。

三层，别混：

| 层次 | 内容 | 放哪 |
|---|---|---|
| **结构** | 有哪些字段、类型、顺序 | 契约（字段清单） |
| **语义** | 单位、取值范围、角度正方向、坐标系、**判定规则** | 契约（§字段表 + §坐标约定 + §异常语义） |
| **阈值** | `conf_min=0.4`、`dist_max=1.2` | **配置** `configs/task.yaml` |

### 8.2 为什么「判定规则」在契约而阈值在配置

因为判定的**规则形式**是双方共同的语义：「`conf` 低于阈值时状态必须置为 `DEGRADED`」——这条要写进契约。
但**阈值取多少**是你内部的事，队友只需按状态响应，不需要知道数字。

### 8.3 判断某个东西放哪的两个问句

1. 「少一个字段会导致什么具体故障？」→ 答不出 = 多余，别加
2. 「这个数字队友需要知道吗？」→ 不需要 = 放配置

### 8.4 字段清单的真正作用

**不是传递数据，而是把隐式假设变成可检查的显式约定。**

所以判据不是「这个数据有用吗」，而是：

- 接收方**知道怎么用**吗？
- 出错时**能被测出来**吗？
- 少它会**导致什么具体故障**？

## Q9 测帧龄是最优解，但它有什么隐患？

### 9.1 隐患清单（老实说，七条）

| # | 隐患 | 后果 | 缓解 |
|---|---|---|---|
| 1 | **测量受显示器限制** | 屏幕刷新率 + 相机曝光导致读数模糊/跳变 | 大字号、缩短曝光、多测几次取中位数 |
| 2 | **只测到「读帧 → 处理完」** | 不含串口与主板 → **不能代替端到端** | 补 L4 的物理测法 |
| 3 | **测的是「理想帧龄」** | 空载测试偏乐观；真实负载下会更大 | **必须在跑满算法 + 开日志的负载下测** |
| 4 | **对着屏幕会触发相机自适应** | 自动曝光/防闪烁改变帧率或分辨率 | 先把自动曝光/自动增益/白平衡**全部关掉并锁定**再测 |
| 5 | **改设置可能静默失效** | 某些后端「设置成功但不生效」，你以为修好了 | **改完必须重测对比**，不信返回值 |
| 6 | **时钟源选错** | `time.time()` 受系统对时跳变影响 | 用 `time.perf_counter()` 或单调时钟 |
| 7 | **单机测不出跨设备偏差** | 视觉与主板时钟不同步时，日志对不上 | 跨设备用同一事件（LED 翻转 / 回传 `t_capture`）对齐 |

### 9.2 最重要的一条（第 3 条展开）

帧龄测量最常见的错误是「空载测出来 40ms，就以为端到端 40ms」。实际上：

- 空载时相机不排队
- 满载时如果处理慢于采集，会开始排队，帧龄可能跳到 300ms+
- **而画面看起来完全正常**（这就是它最阴的地方）

所以：**测帧龄必须在真实负载下测，并且要观察它的分布（P50/P95/P99），不只看平均值。**

### 9.3 它仍然是最划算的第一步

理由不变：半小时能做、不需要场地、不需要队友、**能立刻暴露缓冲排队问题**。所以顺序是「先帧龄，再端到端，最后看控制响应滞后」。

### 9.4 三个测法的定位

| 方法 | 测到哪 | 成本 |
|---|---|---|
| **A 帧龄** | 曝光 → 处理完 | 半小时 |
| **B 端到端物理** | 曝光 → 主板收到（LED 翻转 + 240fps 手机拍） | 半天，需队友 |
| **C 控制响应** | 指令 → 实际响应（相位滞后） | 需上车，最贴近「车好不好开」 |

**为什么必须测**：它同时决定三件事——需要多少 FPS、能不能上重模型、**会不会振荡**（延迟 × 增益 = 不稳定）。
