# vision_qr · K210 扫码节点

只做一件事：读出 4 组三位数任务码，校验，通过串口发给主控。
不参与定位、不做决策、**不知道颜色代表什么含义**。

## 文件

| 文件 | 说明 |
|---|---|
| `main.py` | 主循环：find_qrcodes → 多帧确认 → 校验 → 串口 |
| `qr_validate.py` | **纯逻辑校验，可在 PC 上测**。最高风险代码，17 个用例 |
| `config.py` | 引脚、曝光、校验范围 |

## 串口协议（FROZEN）

| 发送 | 含义 | 主控该怎么做 |
|---|---|---|
| `TASK:156+123+516+231` | 格式+语义都通过，且已多帧确认 | 可采用 |
| `SUSPECT:157+123+516+231` | 解出来了但语义不合法（颜色 7/位置 4 等）→ **可能误读** | 忽略，等人看 |
| `RAW:<原串>` | 格式都不对 | 忽略，仅调试 |
| `HB` | 心跳，每 500ms | 只用来判断节点活着 |

**为什么要 `SUSPECT`**：`find_qrcodes` 在图像模糊时会"解出"一个错误的串。
规则天然给了约束——颜色只能是 1-6、位置只能是 1-3——所以 `157` 这种
一眼就知道是误读。**把误读暴露出来，而不是悄悄下发**，是这一层存在的全部理由。

`CONFIRM_FRAMES = 2`：必须连续 2 帧解出同一结果才上报。挡掉偶发单帧误读。
挡不掉的是「3 被稳定读成 6」这类，只能靠提高图像质量。

## 距离限制（必须实测）

VGA 640×480，二维码 80mm、约 25 模块 → 3.2mm/模块：

| 距离 | px/模块 | 判断 |
|---|---|---|
| 0.4m | 5.6 | 容易 |
| **0.6m** | **3.7** | **可行下限** |
| 0.8m | 2.8 | 勉强 |
| 1.0m | 2.2 | 不行 |

**实测方法**：把 80mm 二维码打出来贴墙，从 1.2m 开始每次靠近 10cm，
记录「第一次能连续 3 秒稳定输出 TASK」的距离。**用实测值排流程，别用估算。**

若距离不够，三个选项按性价比排序：
1. 换更长焦距镜头（视场变窄，需要更准的扫码位，但最有效）
2. 设计更靠近的扫码位
3. 提高分辨率（K210 受 8MB 内存限制，VGA 基本是实用上限）

## 与 MaixCAM Pro 的关系

**两条独立链路，互不知道对方存在。**

```
K210 ──TASK──> 主控 <──增量误差── MaixCAM Pro
```

理由：二维码是一次性事件，不需要和视觉帧同步。绕经 MaixCAM 转发只会
多一个故障点，并且让视觉端被迫知道业务内容。

**代价**：两个 SoC 时间基准不同。所以**不要跨这两个节点做时序分析**。
延迟诊断只在 MaixCAM 一侧做。
